Preface

How to read this chart

A HIPO package has three parts, and this document contains all three in order. The hierarchy chart is given twice: once as the role tree your document uses, and once numbered by module so every function has a citable number. The overview diagram states the input, process, and output of the system as a whole. The detail diagrams do the same for each function, one row at a time.

Numbering is structural, not decorative: a function numbered 7.10 is the tenth function of module 7.0, and every table row below carries the number it was assigned in the hierarchy chart. Names in monospace are the actual tables, columns, functions, and status values in the running system.

One note on form. The overview diagram is drawn in the conventional three-block layout with its process steps numbered in sequence. The detail diagrams are set as IPO tables rather than fifty-eight separate three-block drawings — the same three columns, one row per function, which is how a package this size is normally rendered without losing a reader.

Part 2d · Level 1

Data Flow Diagram — Level 1

Figure 6: process 0 of the context diagram opened up. The same seven external entities sit on the boundary, and every flow that crossed it in Figure 5 reappears here attached to the one child process that actually handles it — which is what makes the two diagrams balance. Building this figure is what surfaced the one flow Figure 5 was missing (Comments, Likes & Support Messages), now added there; that is the point of drawing a level 1 at all. Inside the boundary are the nine processes the code is organised into and the eleven stores they read and write.

What changed since the pre-build draft. The draft had five processes and four stores, and read the system as a feedback box: submit feedback, classify it, report on it. The built system splits along different seams. Identity verification is its own process, not a step inside authentication — it has its own store, its own admin queue, and its own approval decision. Endorsement management is separate from report lifecycle because the agency lifecycle lives on report_endorsements.state, deliberately not on reports.status, and mirrors back onto it. Notification & push delivery is a process rather than a side effect: four other processes raise events into it, and it is the only thing that talks to Firebase. And AI is not one box — classification, moderation and the assistant sit in 4.0, while the predictive outlook is generated in 5.0, which calls Groq on its own account through recommend-actions.

Two flows worth defending in a panel. Staff receive Assigned Reports (Identity Withheld) — not the report queue. They read through staff_reports_view, which returns only reports an administrator has already assigned to their department and nulls user_id on anonymous rows in the database, so the reporter's identity never leaves Postgres. One precision worth holding if a panel presses on it: the view itself does carry ai_urgency, but the staff client never asks for it — staff_repository._reportCols selects fourteen columns and no AI column is among them — so urgency reaching the Administrator alone is a client-side boundary here, not a database one. And the External Agency's only inflow is Scan Token, PIN & Acknowledgement: it holds no account, so it authenticates with a token from a printed QR code plus a 4-digit PIN sent through a separate channel.

Part 2e · Use Cases

UML Use Case Diagram

Figure 9: what each actor can actually ask the system to do. The actors are the ones already established by Figures 5 and 6, and the use cases are the 58 numbered HIPO functions collapsed to the level a use case diagram is drawn at — one oval per goal a person pursues, not one per screen they pass through.

What changed since the pre-build draft. The draft had three actors and read the system as a feedback tool: submit feedback, forward it, report on it. The built system has five. Guest is an actor in its own right — an unauthenticated visitor browses the feed, events and hotlines before any account exists. External Agency holds no account at all: it touches exactly two ovals, and neither is Log In. On the citizen side, feedback is one of four submission paths — reports, suggestions, feedback and concern tickets — and identity verification, the AI assistant and the community feed did not exist in the draft. Municipal Staff no longer forward anything to the Administrator: assignment runs the other direction, which is why no association crosses between them.

Two relationships worth defending in a panel. Confirm Receipt with PIN «includes» Scan Endorsement QR rather than extending it — the agency cannot confirm anything without first resolving the token, because advance_endorsement takes the token and the PIN together. And Post Community Update «includes» Approve Community Post: a staff post is inserted as pending and is not visible in the feed until an administrator approves it, so approval is part of publishing, not an optional extra.

Part 2f · Architecture

System Architecture

Figure 8: where every part of the system actually runs. Read against the pre-build draft, this is the figure that changed the most — not because the plan was careless, but because the platform the system was built on removes a tier the draft assumed.

The one structural correction. The draft had clients → a secure API → an application server → a database. There is no application server. lib/main.dart initialises the Supabase client against the project URL with a publishable key, and the Flutter client speaks to PostgREST, Realtime and Storage directly. Nothing sits between the client and Postgres holding business logic — which means row-level security is not a detail of the data tier, it is the authorisation layer. A panel is entitled to ask what stops a client from reading another citizen’s row, and the answer is a policy in the database, not a check in a middle tier that does not exist.

Why the edge functions are drawn in two boxes. Sixteen exist. Eleven are invoked by the client and it waits for them — login, OTP, the assistant. Five are fired by database triggers through net.http_post and no client ever waits on them: classify-report, classify-feedback, moderate-content, send-push and check-ai-image. That split is the reason a slow or unreachable model cannot fail a citizen’s submission: the row is already committed before the model is asked about it, and the answer is written back afterwards. Drawing all seventeen in one box would hide the property that makes the design defensible.

Part 2 · Overview

0.0  System input, process, output

The whole system stated once, as one input block, one ordered process block, and one output block. Every module diagram in Part 3 is an expansion of a step in this block, and every step here is something at least one module actually performs.

Where the processing happens

The block above says what the system does. This second figure — a system context diagram rather than a HIPO element — says where each of those steps runs, because the process block spans a phone, a database and three external services.

Input

  • Credentials, one-time passcodes, OAuth grants
  • Government ID images, selfie capture, personal details
  • Reports, suggestions, feedback — category, barangay, map pin, remarks, photos and video
  • Concern messages and contact details
  • Community posts, comments, reactions
  • Staff and administrator decisions: status, assignment, approval, sanction
  • QR endorsement tokens and agency PINs
  • Scheduled cron ticks

Process

  • Field validation, rate limiting, duplicate detection on the device
  • On-device ML Kit OCR and profanity screening
  • GPS and timestamp stamping of camera photos
  • Role resolution and row-level security scoping on every read and write
  • Database triggers and webhooks that never block the originating write
  • Edge functions calling Groq GPT-OSS and Sightengine, writing results back
  • Lifecycle transitions, assignment, adjudication and audit logging
  • PDF composition and QR token minting

Output

  • Authenticated, role-routed sessions
  • Verified citizen accounts and unlocked actions
  • Tracked submissions with reference codes and live status
  • AI columns: urgency, sentiment, theme, flags, image likelihood
  • Department-scoped work queues and conversations
  • Analytics dashboards, predictive outlook, report and analytics PDFs
  • In-app notifications and FCM push
  • Endorsement letters with scannable QR, and their acknowledgements

  • Upload to a private storage bucket
  • Administrator inspection and decision

Output

  • verification_submissions row
  • citizen_details record
  • Verified flag and verified_at timestamp
  • Decision notification and unlocked actions

5.0

AI & Moderation Services

Automated

No screen in the app calls this module. Every function is fired by a database webhook, a cron tick, or a fire-and-forget client call, and every one is additive — the on-device rule in 5.7 already produces the same columns, so nothing breaks when a model is unreachable or a quota is spent.

Input

  • Newly inserted report, feedback, post and comment rows
  • Uploaded media paths and public URLs
  • Citizen chat messages
  • Aggregated dashboard data
  • Cron ticks and manual batch invocations

Process

  • Deno edge functions call Groq GPT-OSS or Sightengine
  • Responses constrained to a fixed vocabulary and parsed as JSON
  • Results written back to the source row
  • Bounded retry, then a real error so the client can fall back
  • On-device rules cover any row a model never reached

Output

  • ai_urgency and ai_urgency_reason
  • ai_sentiment, ai_theme
  • flagged, flag_reason, ai_moderated_at
  • AI-image likelihood and status
  • ai_dashboard_insights outlook row
  • Assistant replies to the citizen

External Endorsement Scan

Public · no login

The one screen with no session. An agency officer opens it from the QR printed on an endorsement letter, on a phone, outdoors. It holds no privileges of its own: two SECURITY DEFINER functions are the only things an anonymous visitor can reach, and neither can see a report the token does not name.

Input

  • QR token from a printed endorsement letter
  • Agency officer’s PIN
  • Optional acknowledgement remarks

Process

  • scan_endorsement returns only the report the token names
  • advance_endorsement writes only against a correct PIN
  • No session, no navigation, no app shell

Output

  • An official acknowledgement page
  • State advanced: endorsed → received → completed
  • Progress reflected to the administrator and the citizen
